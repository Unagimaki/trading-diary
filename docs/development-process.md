# Процесс разработки

## От задачи до готового изменения

1. Сформулировать пользовательский сценарий и ожидаемый результат.
2. Определить владельца правила: frontend, domain, infrastructure или несколько слоёв.
3. Проверить существующие контракты, миграции и связанные документы.
4. Изменить domain-модель и тесты бизнес-правил.
5. При необходимости добавить миграцию и repository-реализацию.
6. Обновить HTTP contract и frontend.
7. Проверить негативные сценарии, права доступа и наблюдаемость.
8. Выполнить автоматические проверки и сквозной HTTP-сценарий.
9. Обновить документацию в той же задаче.

## Definition of Done

- Поведение соответствует описанному сценарию.
- Domain-правило не продублировано в UI как источник истины.
- Backend валидирует вход независимо от frontend.
- Проверена изоляция данных разных пользователей.
- Новая ошибка имеет понятный HTTP status/code и попадает в лог.
- Изменение схемы оформлено новой миграцией.
- Пройдены `go test ./...`, `go vet ./...`, frontend lint, tests и production build.
- Для сквозного процесса выполнена проверка через реальный HTTP API.
- Документация и Mermaid-схемы соответствуют коду.

## Где размещать код

| Изменение | Место |
|---|---|
| Бизнес-правило | `backend/internal/domain/<area>` |
| SQL и persistence | `backend/internal/infrastructure/postgres` |
| HTTP endpoint | `backend/internal/transport/http` |
| Новая таблица/поле | `backend/migrations` |
| Entity API и DTO | `frontend/src/entities/<entity>` |
| Страница маршрута | `frontend/src/pages` |
| Самостоятельный блок страницы | `frontend/src/widgets` |
| Общий технический код | `frontend/src/shared` |

## Тестовая стратегия

- Pure function и domain validation — unit tests.
- Repository и миграции — integration tests с PostgreSQL, когда будет выделен тестовый контур.
- Handler/middleware — `httptest`.
- React-компоненты — Vitest и Testing Library.
- Главные пользовательские сценарии — E2E в браузере, когда будет подключён Playwright.

Количество тестов определяется риском. Пересчёты, авторизация, владение ресурсами, миграции и удаление файлов требуют более широкого покрытия.

## Правила миграций

- Применённый файл не редактируется.
- Schema и data migration разделяются, если откат или диагностика сложны.
- Миграция должна работать на существующих данных, а не только на пустой базе.
- Перед production проверяются upgrade с предыдущей версии и состояние `dirty=false`.
- Ручное исправление production-данных оформляется воспроизводимой миграцией или отдельной контролируемой операцией.

## Документационное правило

Архитектурный документ объясняет устойчивое устройство, process-документ — последовательность действий, product rules — бизнес-формулы, API-документ — внешний контракт. Один факт должен иметь одно основное место, остальные документы ссылаются на него.
